## 3. Starting the environment

- [x] 3.1 Add `InitError::RuntimeLoad { path, source: ort::LoadDynamicError }`, `InitError::RuntimeStart { path, source: ort::Error }` (design D7) and `InitError::RuntimeUnavailable { path, reason: String }` (design D9). Verify with unit tests that `RuntimeLoad`'s `Display` names the library path and its `source()` reaches the underlying `ort` error — built from `ort::LoadDynamicError::MissingApi`, whose fields are public, so no unit test touches `ort`'s load global — and that `RuntimeUnavailable`'s `Display` names both the path and the recorded reason. `RuntimeStart`'s `Display` is asserted in the live test of 4.2 instead: every `ort::Error` constructor goes through `ortsys![CreateStatus(..)]` and needs a runtime already loaded, so it cannot be built on a runner that has none.
- [x] 3.2 Implement `runtime::start(name: &str, library: &Path) -> Result<(), InitError>`: `ort::init_from` with an absolute path, `with_name(name)`, `with_telemetry(false)`, `commit()` with its return value ignored and a comment saying why, then `Environment::current()` to force creation eagerly and `set_log_level(LogLevel::Warning)`, letting the handle drop (design D3, D4, D6). Verify it compiles and the tests in 3.3 pass.
- [x] 3.3 Add the D9 latch to `runtime.rs`: a `static FAILED_LOAD: Mutex<Option<Failure>>` holding the path and the `Display` of the first failed load, taken for the whole of `start`, so a process that has already failed returns `InitError::RuntimeUnavailable` without reaching `ort` again. Verify against the measured defect — after one failed `ort::init_from`, every later call in that process returns `Ok` whatever path it is given, because `ort`'s `OnceLock` marks a `call_once_force` closure that returned `Err` as completed and then hands out a reference to uninitialized memory.
- [x] 3.4 Unit-test the two failure paths reachable without a real runtime, each in a process of its own: a path that does not exist, and a `tempfile` that is not a shared library. Verify both produce `InitError::RuntimeLoad` naming the path attempted, and that a third process proves the latch — a failed load followed by a second `start` against a different path answers `RuntimeUnavailable` rather than the `Ok` `ort` alone would give. Each re-runs the unit-test binary against one `--exact` test name under a marker variable, as `tests/reexec_linux.rs` does, since `ort`'s load global is process-wide and Cargo runs a crate's unit tests in one binary on concurrent threads (design D9).
- [x] 3.5 Call `runtime::library_path` and `runtime::start` from `Opai::initialize` after the installs complete and before the handle is built, on `tokio::task::spawn_blocking` as slice 1 does for the archive expansion (design D3). Verify `Inner` is unchanged, every existing slice-1 and slice-2 test still compiles and passes unmodified, and `Opai::install` keeps its current signature.

## 4. Lifecycle coverage

- [x] 4.1 Add an integration test pinning `ort`'s actual load-global semantics, which is what D5 and D9 both rest on and what no runner can reach through a real load: a second `ort::init_from` against a different path in the same process does **not** report the first call's failure but returns `Ok` having loaded nothing (design D9, measured). Verify it lives in its own file under `opai/tests/` with `ort` as a dev-dependency at the same pin, since the global it exercises is process-wide, and that it says plainly that a failure here means `ort` has fixed the defect and D9's latch should be re-read rather than that this crate has broken.
- [x] 4.2 Add an `#[ignore]`d test that installs the pinned runtime into a temporary directory, starts the environment against it, asserts a second `runtime::start` in the same process also succeeds and leaves the first environment in place, and asserts `InitError::RuntimeStart`'s `Display` names the library path — which is the one place an `ort::Error` can be constructed at all (design D8, task 3.1). Verify with `cargo test -p opai -- --ignored` on macOS/aarch64 and record the result; document in the test why it is ignored (a ~175 MB download per run, the same reason as Go's `internal/deps/live_manual_test.go`).
